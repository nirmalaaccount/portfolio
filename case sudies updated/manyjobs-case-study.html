Revamping a live product: from telling recruiters what it does, to showing them

ManyJobs is Matrimony.com group's live recruitment platform for entry-level Sales, Service and Manufacturing hiring, currently serving Tamil Nadu. The product already works — candidate match scoring, a bilingual English/Tamil app, WhatsApp contact, and locality filters are all shipped. My job was a visual and structural revamp of the recruiter-facing marketing page and dashboard preview: building a shared component system, and replacing descriptive benefit cards with an actual working preview of the product itself.

Context

A live product, checked directly before touching a pixel

Before redesigning anything, I checked recruiter.manyjobs.com/register directly rather than assume what it did or didn't do. It's a working product: recruiters register with just a mobile number, post free, and get access to a pool the site states at 15,000+ candidates, with match-ranked applicants, direct call/WhatsApp contact, locality filters, and bilingual (English/Tamil) job posting — already live, already serving hiring partners across cities including Chennai, Coimbatore and Madurai.

A note on scope

This is a design revamp of an already-shipped product, not a 0→1 concept and not a research-backed study. I didn't run recruiter interviews or see usage analytics. What I can defend directly is the component system and the specific presentation decisions in this case study — I'm not claiming more than that.

Early thinking

The one decision that changed the whole approach

Before building the component system, I had to resolve a more fundamental question: was the problem with ManyJobs a visual one, or a structural one? The answer changed everything downstream.

First framing — visual polish

Redesign the marketing page aesthetics

Initial instinct: the live site looks dated — clean up the typography, refresh the color system, tighten the spacing. A typical visual revamp.

Rough layout idea at this stage: Hero headline → Feature grid (3 benefit cards) → Stats → Testimonials → CTA

The benefit cards described match scoring, bilingual, WhatsApp — but as text labels next to icons. Standard SaaS structure.
What made me stop

Checking the live product directly before designing anything, I saw it already did these things — match scoring was live, bilingual posting was live. The problem wasn't that the features didn't exist; it was that the page was describing them rather than showing them. A visual polish pass wouldn't fix that.

Second framing — chosen

Replace description with demonstration

If the features are real and working, the design job is to make them visible — not describe them in benefit cards.

What changed structurally: — The "Match scoring" benefit card → an actual dashboard preview with ranked candidates and percentages
— The "Bilingual support" feature label → a live side-by-side field demo showing Job title / வேலை
— The stats band → real verified numbers, not placeholder copy
This framing decision — show vs. describe — is what drove the component system, the dashboard section, and the bilingual demo that followed. Everything else in this case study flows from it.

Component system

Five reusable pieces, not one-off screens

Before touching individual sections, I built a small shared component set — Button, MetricItem, FeatureCard, StepCard, QuoteCard — instanced throughout both the desktop (1440px) and mobile (360px) frames, so a 12-section page stays visually consistent without every section being a hand-copied frame.

01

Button

Three styles — Primary, Inverse, Ghost — reused across header, hero, CTA banner and final CTA instead of one-off styled elements each time.

02

FeatureCard / StepCard / QuoteCard

Instanced across the Features grid, the 5-step "How it works" row, and the Testimonials section — six feature cards and five step cards, all instances, not copies.

03

MetricItem

One component instanced four times in the stats band on both breakpoints, so a metric update only touches one definition.

Recruiter flow

How a recruiter moves from posting to contact

This is the core task flow the dashboard preview is designed to support. Mapping it explicitly helped me decide what the dashboard needs to show and — equally — what it doesn't need to show.

1

Register and post a job — one field entry

The live product's registration is mobile-number-only — no email, no profile setup. That's already the right decision and the revamp keeps it. A recruiter posting a sales role in T. Nagar needs to be posting within 2 minutes of arriving, not filling in a company profile. Design implication: the hero CTA goes directly to the registration field, not to a feature overview.

2

Review applicants — ranked by match score

Once a job is live, the recruiter's primary question is: who applied, and who should I call first? The dashboard answers this with a ranked list — match percentage, location, experience — visible without opening any candidate profile. Design implication: the dashboard preview in the marketing page shows this exact view, because it's the core value proposition made visible.

3

Contact — one-tap Call or WhatsApp

For entry-level Sales and Manufacturing roles, the recruiter is often on the move — at a job fair, visiting a site, between calls. Direct contact from the list view without a separate profile page is the right interaction. Design implication: the dashboard preview shows Call inline in the candidate row, not behind a "View profile" step.

4

Shortlist and track — sidebar navigation

After initial contact, a recruiter needs to track which candidates are shortlisted and follow up. The sidebar order — Applicants → My Jobs → Shortlist → Reports — follows the task sequence, not alphabetical or by importance ranking. Design note: I could not verify the live logged-in dashboard against this flow, since it sits behind authentication. This sequence is a design hypothesis.

Key decisions

Demonstrate the value, don't describe it

1

Show the dashboard itself, not a card describing it

The live site communicates match scoring through a benefit card. I replaced that with an actual dashboard preview — ranked applicants, real match percentages, inline Call action — so the feature is demonstrated, not summarised.

2

Give the existing bilingual feature a concrete visual proof

The live product already supports English/Tamil job posting. I designed a dedicated section with a side-by-side field demo — Job title / வேலை — showing the actual posting form in both languages at once, so the feature reads as evidence rather than a label next to an icon.

3

Keep the one-field registration, make it consistent everywhere

The live site's mobile-number-only registration is already the right pattern — low friction, no signup gate. I kept it as a reusable component instanced in both the hero and the final CTA, rather than two independently built forms.

4

Sidebar IA follows how a recruiter actually works a role

Applicants → My Jobs → Shortlist → Reports, in that order — because a recruiter filling a role thinks "who applied" before "which job" and long before "what's the report." This is a proposed structure for the dashboard preview; I could not verify it against the live logged-in product, which sits behind recruiter authentication.

Mobile

A recruiter checking applicants between site visits

For roles like Sales and Manufacturing, a lot of recruiter activity happens on the move, not at a desk — and the live site itself is registration-first on mobile. The mobile frame (360px) keeps the same component instances as desktop but reorders the hero so candidate cards sit directly below the one-field registration module, and the dashboard's sidebar collapses into the same four-item task order (Applicants → My Jobs → Shortlist → Reports) rather than hiding behind a hamburger menu.

Reflection

What this is, and what I'd validate next

This is a Figma revamp of a live, already-shipped product — not a 0→1 concept, and not something I've validated with real recruiters myself. Worth noting: the live site already carries strong verified social proof — named client quotes from Netambit, Paytm Services, Thangamayil Jewellery and Pumo Technovation — real evidence I didn't need to invent, and worth preserving in any final version rather than replacing with generic placeholder testimonials.

If I were taking the dashboard preview further, the question I'd want answered first is whether a bare match percentage is enough for a recruiter to act on, or whether they need a visible "why this match" reason (skills, location radius, availability) before they'll trust it enough to pick up the phone. That's a five-minute conversation with a real recruiter, and it's the test I'd run before anything else — not another visual pass.

Post-design cognitive walkthrough

A cognitive walkthrough from three recruiter perspectives — a first-time HR manager, a returning recruiter, and a job seeker who landed on the wrong page — surfaced the most significant gap I'd missed: the entire page is oriented toward new registration with no visible login path for returning users, who are actually the most valuable users since they've already been converted. A returning recruiter typing their number doesn't know if they're logging in or creating a duplicate account. One line — "Already registered? Enter your number to sign in" — resolves it entirely. The walkthrough also found that "15,000+ candidates" needs geographic context to be meaningful for a recruiter hiring in Chennai specifically, and that the dashboard preview doesn't show the locality filter the live product already has — the one question a recruiter asks immediately after seeing the ranked list is "can I filter by location?"

The easy version of this project was making the page look clean. The harder version was resisting the urge to explain the bilingual support in a sentence when showing it in the actual form fields said it faster and more convincingly.
